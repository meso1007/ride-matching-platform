# 要件定義（00-requirements）

ステータス: WIP（機能要件の正常系＋異常系シーン1〜3まで合意済み。残りのシーンの異常系・非機能要件・規模見積もりはこれから）

## 機能要件

### ライダー（乗る人）

1. 行き先を入力し、ルートと料金の見積もりを見ることができる
2. 配車をリクエストできる
3. 決まったドライバーの情報（名前・車種・ナンバー・評価）を見ることができる
4. ドライバーの現在地と到着予測時刻を、地図でリアルタイムに見ることができる
5. 配車のステータス（ドライバー決定／迎えに移動中／到着／乗車中／完了）を確認できる
6. 到着後、事前登録した支払い手段で自動決済される
7. ドライバーを評価でき、問題があった場合は通報できる

### ドライバー（運転する人）

1. オンライン／オフラインを切り替え、「今フリーです」という空き状態をシステムに伝えることができる
2. 自分の位置情報を継続的に送信する
3. システムから割り当てられた配車リクエストを受諾／拒否できる
   - ドライバーがライダーを選ぶのではない。割り当てはシステム側が行う（選べるようにすると短距離ばかり選ばれる等、ライダー体験が崩れるため）
4. ピックアップ地点までのナビ（ルート）を見ることができる
5. 到着・乗車開始・完了などのステータスをボタン操作で進めることができる
6. 送迎ごとの報酬と、売上合計を確認できる

### システム（マッチング）

1. ライダーの近くにいるフリーなドライバーを探し、配車を割り当てる
2. 前提：エリア内に一定数のドライバーがいること。ライダーの需要がドライバーの供給を溢れる状態は避ける
   - 需給が崩れた場合の扱い（待たせる／料金を上げる等）は未決定事項
3. 料金は事前確定とする：リクエスト時に確定し、走行距離・時間・経路の違いでは変動しない（ドライバーの遠回りや渋滞で料金が膨らまず、ライダーが安心できるため）

## 異常系

前提：配車モデルは「システム割当型（モデルA）」。ライダーが選ぶのは車両クラスまでで、ドライバーの割り当てはシステムが行う。

### シーン1：配車リクエスト〜ドライバー確定

- **ライダーがキャンセルする**（マッチング前／マッチング後）：配車はキャンセル状態になる。相手には「エラー」ではなく状態の変化として通知する（キャンセルは異常終了ではなく正常な遷移の1つ）。割り当て済みのドライバーは即フリーに戻る
- **ドライバーが拒否する**：ライダーには見せず、次の候補ドライバーに割り当てる
- **ドライバーが無応答**：7秒でタイムアウトし、次の候補ドライバーに割り当てる。ライダーの画面は「探しています」のまま
- **近くにドライバーがいない**：探索半径には上限を設ける（目安 20km、要調整。実際は小さい半径から段階的に広げる方式を検討）。範囲内に候補がいない、または全員に拒否・タイムアウトされたら、ライダーに「利用できません」と表示して終了する
- **同じドライバーへのリクエストが同時に競合する**：先着の1件だけが成立し、もう1件は別のドライバーに回す。「先着」をどう保証するかが設計課題（→ 学習目標「競合制御と原子性」）
- **ドライバーの位置情報が古い**（レビューでの追加）：フリーと表示されていても位置が数分前だと誤ったマッチングになる。位置の鮮度（最終更新時刻）も候補の条件に入れる

### シーン2：迎え〜乗車

- **ライダーがキャンセルする（ドライバー移動中）**：キャンセル料が発生する。金額はドライバーの移動距離（または経過時間・状態）に応じて決まる（料金ルールの詳細は未決定）。ドライバーはフリーに戻る
- **ドライバーがキャンセルする**：ライダーに「キャンセルされました」と通知し、次のドライバーを再検索する。ライダーの待ち時間はリセットされる点がシーン1の拒否と異なる
- **ライダーがピックアップ地点にいない（ノーショー）**：ドライバーはメッセージ／電話で連絡できる（電話番号は中継して秘匿する）。到着時刻から待ち時間を計測し、一定時間（目安5分）待っても現れず連絡も取れなければ、ドライバーはノーショーとして終了でき、ライダーにペナルティ（キャンセル料・アカウント上の記録）が付く
- **ドライバーが来ない**：位置情報から「ピックアップ地点に近づいていない」ことを検知できる。ライダーは無料でキャンセルできる
- **操作の競合（到着 vs キャンセルなど）**：サーバーに届いて記録された順番を公式の順番とする。先に処理された状態遷移が確定し、後からの操作は現在の状態で受け付け可否を判定する（キャンセル確定後の「到着」は弾く／到着確定後のキャンセルは到着後ルールで処理する）

### シーン3：送迎中

- **途中で降りたい（ライダー都合の途中終了）**：事前確定料金のため、見積もり全額を請求する。配車はその場所で完了扱いになる
- **目的地が間違っていた**：当初の配車は全額で確定する。正しい目的地へは、その場所から新規の配車として登録し直す
- **ドライバーが道を間違えた／遠回りした**：事前確定料金のため金額は変わらない（ライダーが損をしない）
- **位置情報が届かない（トンネル等）**：料金は距離に依存しないため影響なし。ライダーの画面では最終位置を表示し続ける。走行記録が欠けないよう、ドライバーの端末が位置をバッファし、再接続時にまとめて送信する
- **目的地変更と完了の競合**：サーバー到着順で裁く。完了が先に確定したら目的地変更は受け付けず、行き先へは新規配車として扱う（目的地間違いのケースと同じ形）

## 未決定・これから決めること

- 異常系の残りシーン：到着〜決済（決済失敗、二重課金など）
- キャンセル料の詳細（無料の猶予時間、金額の計算方法）
- 非機能要件：レイテンシ目標、可用性、整合性の要求
- 規模の見積もり：ドライバー数、位置更新の頻度、ピーク時のリクエスト数
